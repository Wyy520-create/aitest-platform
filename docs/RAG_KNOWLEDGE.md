# 测试领域知识库（RAG 语料）

> 本文件是 RAG 问答系统的检索语料之一。每个 `##` 小节切为一个知识片段（chunk），
> 供 BM25 检索。因此写作要求：**每节自包含**——单独被召回时就是完整可读的知识点。

## 用例设计：等价类划分

等价类划分是把输入域按"程序处理行为相同"分组，每组取代表值测试。
合法等价类与非法等价类都要覆盖。例如用户名长度契约 3-32 位：
合法等价类取中位值（如 8 位），非法等价类取 2 位、33 位、空串。
边界值分析常与等价类搭配使用：取边界本身（3、32）及边界两侧（2、33）。

## 用例设计：边界值分析

边界值是缺陷高发区。经验统计：大量缺陷出现在输入/输出的边界上而非中部。
对分页接口，page 的典型边界是 1（首页）、总页数（末页）、0 和 -1（非法）。
对长度类契约，测 min-1、min、max、max+1 四个点。
本项目的 BUG-05 正是 page=0 未校验导致的静默错误——边界值用例抓的就是这类问题。

## 用例设计：异常参数与参数校验

异常参数用例验证系统对非法输入的防御：类型错误（字符串传给整型字段）、
缺失必填字段、非法值（负数、零、超长）。规范系统应返回 422/400 并说明原因，
而不是静默接受或崩溃。本项目的 BUG-04 是购物车数量未校验负数/零：
加购 quantity=-5 竟返回 201，下单时总额变负——平台倒贴钱。

## 安全测试：水平越权

水平越权指同权限级别的用户 A 访问用户 B 的资源（对比垂直越权：普通用户访问管理员资源）。
检测方法：注册两个用户，A 下单得到订单 id，用 B 的 token 请求该订单，
期望返回 403/404，若返回 200 且带数据即越权缺陷。根因通常是查询时只按资源 id
过滤、漏了 owner 条件。本项目 BUG-01 即此类：/api/orders/{id} 未校验订单归属，
用户 B 可以用 id 枚举读取任意用户订单。

## 安全测试：用户枚举防护

登录失败信息不应区分"用户不存在"与"密码错误"——否则攻击者可枚举出
系统里有哪些注册用户。检测方法：对不存在的用户与存在但密码错的用户分别登录，
断言两者的错误信息完全一致。这类用例属于安全类回归，改动登录逻辑时必跑。

## 安全测试：JWT 鉴权

JWT 由三段组成：header.payload.signature。服务端用密钥对前两段做 HMAC-SHA256
签名，客户端不可伪造（改 payload 后签名校验失败返回 401）。测试点：
伪造签名 token 应 401、过期 token 应 401、无 token 访问受保护接口应 401、
响应体绝不能泄露密码哈希。本项目用 HS256 + 2 小时过期。

## 并发测试：超卖与丢失更新

秒杀场景的典型缺陷：多线程同时读到相同库存（如都读到 5），各自下单成功，
导致库存 5 件卖出 10 单（超卖）。根因是"检查库存"与"扣减库存"两步不原子
（丢失更新）。检测方法：N 个线程并发下单库存 M 件的商品（N>M），
断言成交数 <= M 且最终库存 = M - 成交数。修复方式：数据库行锁
（SELECT ... FOR UPDATE）、乐观锁（version 字段）或原子 UPDATE。
本项目 BUG-02 即此缺陷，测试用 ThreadPoolExecutor 10 线程打库存 5 的商品。

## 精度问题：浮点数金额

二进制浮点数无法精确表示 0.1、19.9 等十进制小数，累加会产生
0.1+0.2=0.30000000000000004 式误差。金额场景必须用 Decimal 或整数分。
检测方法：购买 3 件 0.1 元商品，断言订单总额 == 0.3（会失败，
实际 0.30000000000000004）。本项目 BUG-03 即此缺陷，订单金额用 float 累加。

## 缺陷清单：本项目 5 个注入缺陷

mini-mall 被测系统故意埋了 5 个真实缺陷，全部被自动化套件命中：
BUG-01 水平越权（订单详情不校验归属，用户 B 可读用户 A 的订单）；
BUG-02 并发超卖（库存检查与扣减不原子，10 并发买 5 库存全成交）；
BUG-03 金额精度（float 累加，0.1 x 3 = 0.30000000000000004）；
BUG-04 参数校验缺失（购物车数量接受负数/零，订单总额为负）；
BUG-05 分页静默错误（page=0 不报错，负偏移量被静默当作 0）。
详见 docs/BUGS.md，含每个缺陷的触发方式、根因分析与正确写法。

## 项目结构：aitest-platform 总览

aitest-platform 是智能接口测试平台，四大组件：
1. sut/ —— mini-mall 被测系统（FastAPI + SQLite，含 5 个注入缺陷）
2. engine/ —— Pytest 分层测试引擎（cases→api→core 分层，45 条用例）
3. platform/ —— 测试平台（FastAPI 后端 + Vue3 CDN 版前端），
   含用例管理、执行调度、AI 用例生成与评审流、RAG 问答
4. compose + CI —— docker-compose 四服务编排，GitHub Actions 双 job
本地启动：docker compose up -d --build，平台入口 http://localhost:3000（admin/admin123）。

## 测试引擎：分层架构

Pytest 引擎按三层组织：cases（用例层，只写业务断言）→ api（接口对象层，
封装每个接口的请求细节）→ core（HTTP 客户端与工具）。
conftest.py 用 fixture 把三层组装注入用例，用例文件不 import 底层类——依赖倒置。
分层价值：接口路径/字段变更时只改 api 层，几十条用例零改动。
执行入口 run.sh 固化 PYTEST_DISABLE_PLUGIN_AUTOLOAD，规避本机插件干扰。

## 平台：双执行器设计

平台支持两类执行：suite（代码化套件，跑 engine/ 的 Pytest 用例，
表达力强适合核心回归）与 config（配置化用例，数据库里的 JSON 用例，
网页上创建即时生效，非程序员可用）。suite 用 subprocess + junitxml 解析，
config 用 requests 按用例描述逐条执行。这对应业界的"代码型 vs 平台型"
用例双轨模式。

## 平台：AI 用例生成与评审门禁

AI 用例生成链路：拉取被测系统 OpenAPI 文档 → 瘦身组 Prompt →
LLM 输出结构化 JSON 用例 → 解析入库（draft 状态）→ 人工评审 →
采纳后进入 config 执行。评审门禁是核心原则：LLM 产出按不可信数据
（untrusted output）处理，采纳率指标度量 AI 质量。未配 API key 自动
降级 MockLLM，全链路可演示。接入真实 LLM 见 docs/LLM_SETUP.md。

## CI：缺陷注入项目的断言姿势

缺陷注入仓库的 CI 不能断言"测试全绿"——套件跑出 7 条失败是正确表现
（全部命中注入缺陷）。正确做法是断言"预期签名"：45 用例 / 38 通过 /
7 失败 / 7 条失败全部为 test_bug 前缀用例。scripts/verify_suite.py
校验该签名，任何注入缺陷被误修、或套件被改坏，CI 立刻报警。
GitHub Actions 还有 platform-e2e job：HTTP 走登录→触发→轮询→断言平台统计。

## RAG：检索增强问答原理

RAG（Retrieval-Augmented Generation）先检索后生成：用户提问 →
检索器从知识库召回最相关片段 → 片段拼进 Prompt → LLM 基于片段作答。
价值：回答有出处（可验证、降幻觉）、知识可热更新（改文档即可，
不用重训）。本平台的检索器是自实现 BM25（中文用字符 bigram 分词，
无需分词库依赖）；生成层无 key 时降级为"直接返回检索片段"。
质量评测维度：hit@k（期望片段命中率）、MRR（期望片段排名倒数均值）、
拒答正确率（知识库外问题不硬答）。

## 测试数据准备：数据工厂模式

测试前置条件（如把秒杀库存重置为 5）需要"摆数据"。两种途径：
本地开发直连数据库（灰盒，最快）；容器/CI 环境引擎与被测系统隔离，
走 HTTP 数据工厂接口（SUT 仅在 TEST_MODE=1 时注册 /api/dev/* 路由，
生产环境该路由根本不存在——不是鉴权挡住，而是没有这个面）。
验证阶段始终纯黑盒：只通过 HTTP 断言被测行为。
